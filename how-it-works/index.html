Bookish · architecture

How the data flows, and where the model actually sits

Bookish has two systems that share one dataset. A language model builds the data on my laptop; the site that readers use contains no model at all. Keeping those apart is what makes the spoiler boundary a guarantee rather than a request.

The reading position is the one input the data cannot supply, so the chart asks for it before drawing anything — which book have you finished? Not which you are reading: someone halfway through book three has finished book two, and book two is what is safe to show them. The answer is remembered per series, and dismissing the dialog means book one, because a reader who closes it has told you nothing and the safe reading of nothing is the beginning.

Three things about this shape are deliberate. The model never touches book text — the corpus is plot beats, so nothing copyrighted enters the repo. Human judgement is a file, not a memory: corrections are re-applied after every extraction, because the Carrion Swift merge was destroyed three times by re-runs before it was written down. And everything reader-facing hangs off one function — if gate() is right, four surfaces are right.

Two systems, one dataset

The thing most people assume is a chatbot on a website. It isn't. The model runs once, on my machine, to produce data — and then never runs again.

Why this matters more than it sounds. A chatbot asked politely not to spoil you can be talked out of it. Here the model never sees the reader's question, and the reader's code never sees data past their reading position. There is no instruction to ignore.

The pipeline, stage by stage

Each chunk of source text passes through three agents. Two of them are a language model; the third is deliberately not.

01

Plan

The model is asked only which characters the passage names, plus a one-line summary. The plan is checked against the text before anything expensive happens — a plan naming people who aren't there is caught here, cheaply.

model
02

Extract

One agent per chunk, running concurrently, each seeing only its own chunk so nothing from book 3 can bleed into a book 1 extraction. Output is constrained to the schema, so malformed JSON isn't a failure mode.

model
03

Verify

A second pass re-reads the same chunk and rules on every relationship the extractor claimed. It's told to answer unsupported when unsure, because the two mistakes don't cost the same: a missing edge is a gap, a wrong edge is a false statement on the chart.

model
04

Resolve

Merges the chunks and settles contradictions — a definite status beats unknown, a later chunk is later in the story. No model: these rules are clear, and asking one to arbitrate would add variance without adding judgement. Every decision is logged anyway.

code
05

Validate

Zod schema plus referential integrity: every relationship endpoint must exist, every killed victim must actually be dead, family labels must be kinship terms. Fails the build rather than shipping bad data.

code
06

Score

The result is compared against 144 hand-labelled characters and 245 typed relationships. Precision, recall and F1 per relationship type, plus a count of any entity named that the reader couldn't know yet.

code

One gate, four callers

Every read of the data goes through the same function. A second implementation would be a second chance to get it wrong.

Given a series and a reading position, gate() returns only what a reader at that point has met: characters whose first book has arrived, relationships whose both endpoints are visible, events up to that book. It also swaps in what the reader believes — Brennan reads as dead through book 1 because that's what you think until the final paragraph of Fourth Wing, and Rip is just Rip until the end of Glint.

That last part used to be a half-truth. Belief-swapping lived in a separate present() function, so it only protected callers that remembered to use it — the ask box and the MCP server did, and the chart renderer did not. It read the gated characters and drew them, which meant a hidden prince was drawn under his real name and title two books before the reveal, with every spoiler test passing. Resolution now happens inside gate(), so the rule protects everyone rather than everyone who opts in.

FieldWhat the gate does
charactershidden until their first book arrives
relationshipshidden unless both endpoints are visible — so a hidden character can't be inferred from a dangling line
status · identity · role · affiliationreplaced by what the reader believes, until the book that reveals otherwise
biographieswithheld entirely below the final book — 25 of them name someone who hasn't appeared yet

A refusal shouldn't confirm anything either. Asking the MCP server about a book-3 character at book 1 returns "no such character at your reading position" — not "that character appears later", which would leak that they exist. The reply doesn't echo your query back either.

Invented edges went to zero and precision rose seventeen points, but rejecting a claim costs a true positive when the verifier is wrong, and F1 punishes that harder than it rewards precision.

F1 is the wrong measure for this product. For a chart people read to avoid being misled, a missing edge is a gap and a wrong edge is a false statement. Those aren't worth the same, and F1 weights them equally. Better to say so than to quietly report whichever number looked better.
